How Tilltrend works

An AI analyst is only useful if you can trust the numbers. Tilltrend's design starts from the assumption that you shouldn't have to trust. You should be able to check.

The Ask flow

You type a question: "What was total revenue?", "Compare June and July 2013 revenue", "Which countries drive revenue?". What happens next is deliberately split in two:

  1. The AI chooses, it never calculates. The AI picks from a fixed list of figures Tilltrend has written rules for (revenue, orders, average order value, monthly revenue, cohort retention, customer lifetime value, product performance, repeat rate). A pick that breaks the rules is rejected and logged; the AI gets one chance to correct itself, then Tilltrend stops and asks you what you meant.
  2. Tilltrend's code does the calculating. The query for that figure, written down once in Tilltrend's rules, runs on your store's data in Tilltrend over a read-only connection. The result is written into a receipt: the query, its inputs, the rows, which build of your data it ran on, and a hash of all of it, a fingerprint that changes if anything in it does.

The answer you see keeps two parts visibly apart. The figures are drawn by code directly from the stored receipts, and the AI cannot edit them. The explanation, which you ask for with the Explain button, is the AI's own writing and is labeled "written by the AI, not part of the receipt". The figures in it are checked against the receipts before you see it. If a figure isn't in the receipts, the draft is rejected and rewritten; fail twice and Tilltrend's own note appears instead. This has caught a real violation in testing. The bad draft never shipped.

Receipts and replay, simply

Every figure in an answer carries a receipt id and a hash, like rcp_c60c017f43c346328383448a66088735 | sha256:371834e1a0a6100a. Replaying a receipt runs its exact query again, with no AI anywhere in the loop, and grades the result:

VerdictMeaning
MATCHSame query, same data, same numbers. The answer still holds.
STALEYour store's data changed since the receipt was written; the receipt was honest for the data it saw.
FAILThe receipt doesn't hold up when run again, including receipts someone edited to lie coherently.
ERRORThe receipt file is damaged; Tilltrend refuses to grade it rather than guess.

This is tested on purpose: our checks forge receipts five different ways (edit the rows, recompute the hashes to match, change the worked-out values, delete caveats) and confirm each forgery fails in exactly the way predicted. Commands and observed results are on the evidence page.

Honest refusal

When the data to answer a question doesn't exist, Tilltrend says so, in its own written words, not the AI's. Verbatim, from a real run on 2026-10-31:

Real output · python app\scripts\ask.py "Show me the conversion funnel"
RECEIPTED FACTS
===============
(no receipts this turn)

REFUSAL (governed text, not model prose)
========================================
Not yet supported: your store traffic and conversion funnel, from a first visit through product views, add to cart and checkout to a purchase. Tilltrend sees your orders, not what shoppers do before they buy, so it won't guess.

source: Tilltrend's written rules for its numbers. These aren't the AI's words.

No stand-in figure, no plausible-sounding guess. Orders alone can't show what shoppers did before they bought, so Tilltrend refuses rather than approximates.

The admin app today

Eight pages exist now. Every figure on them is worked out by Tilltrend's written rules each time the page opens, from your store's data as of the last sync, and each headline figure has a footnote naming the metric behind it.

PageWhat it shows
OverviewHeadline figures (total revenue, orders, average order value, repeat-rate split, the spread of customer lifetime value) plus a panel showing which build of your data produced them, over what dates.
TrendsSales over time at the grain you pick (day, week, month, quarter, or year) as a line and area chart with a running total, a moving average, and the change from the period before and from the same period last year. A period with no sales reads as an honest 0, a part period at either end is flagged, and a change with no earlier period says so rather than inventing one.
ProductsTop products by revenue as a bar chart, with a table of units, orders and distinct buyers and a breakdown by category.
CohortsThe full cohort-retention table; empty cells are labeled "zero, not missing", with the cohort definition quoted on the page.
AskA chat surface. An answer opens with a readable card built from the stored receipt: a single figure shown large, a multi-row result as a real table, money in your store's currency. The exact audited text sits one click away, unchanged to the character. Beneath an answer with figures sit the exact SQL Tilltrend ran and its receipt, which you can download as a CSV. The AI's optional explanation stays visibly labeled as the AI's, with a line saying whether its figures passed the check.
ExportThe BI export: a zip of CSVs with a data dictionary that shows how the tables join, plus a personal API token that opens exactly one read-only endpoint for BI tools.
ReportThe Store Data Health-Check as a printable page, one click from the dashboard (Ctrl+P to PDF): the same report as the public sample, rendered on your own store.
AuditThe audit log, which is only ever added to: every question, every step the AI proposed, every rejection and refusal, with the build of your data on each row.

What deliberately doesn't exist: there are no Funnel, Experiments, or Insights pages, not even mock ones. The nav carries a single greyed, non-clickable note: "Funnel: requires event data". A page ships when the capability is real, not before.

Not supported yet

  • Session funnel (visits → views → cart → checkout → purchase): Tilltrend sees your orders, not what shoppers do before they buy. Refused honestly today, as shown above.
  • Promo performance (how each discount code performed): revenue takes every discount off, but Tilltrend doesn't keep which discount it was.

Architecture, for technical readers

A real layered warehouse

Store data lands in a medallion warehouse on PostgreSQL: bronze (raw, as extracted), silver (cleansed: deduplication, invalid-date nulling, amount repairs, all rules documented), gold (a star schema plus analytics views: monthly revenue, cohort retention, customer LTV, product performance, repeat rate). Rebuilds are single-transaction and reproducible: every build records its identity and a deterministic content fingerprint, so two builds of the same data are provably identical. A 33-check quality suite guards each layer, and the whole warehouse was ported DuckDB → PostgreSQL with every metric verified exact across engines.

Governed metrics, one source of truth

Every metric the agent can cite is defined once: id, plain-language definition, exact formula, grain, lineage, canonical SQL, and real caveats (including the dataset's known gaps, like 19 invalid-date sales lines worth 4,992 of revenue, documented rather than hidden). Definitions change only via dated decision entries. If a question needs a formula that isn't governed, that's a new-definition request, not a judgment call the model gets to make.

The model never touches data

The law of the system: the model proposes tool calls and writes prose; everything else is deterministic code. SQL comes from the governed registry, runs over a connection that is read-only twice over (database-level read-only transactions plus an SQL gate allowing single SELECT statements only), with statement timeouts and row caps. Every call, rejection, and refusal is written to an append-only audit log. The receipts machinery itself is tested by an adversarial verification gate: interception tests prove the receipt contains the very objects the query executed, fault-injection proves forgeries fail, renderer tests prove what's stored is what's shown.

All of the above is checkable: every claim, with its command, on the evidence page.
